## MVE — Slint 1.18.1 (winit backend, software renderer, Rust API) as an on-demand settings process, with rfd 0.17.2 native folder picker and a JSON-RPC client over a local socket
- **Source**: https://crates.io/crates/slint 1.18.1 (published 2026-09-21; MSRV 1.92; licence expression `GPL-3.0-only OR LicenseRef-Slint-Royalty-free-2.0 OR LicenseRef-Slint-Software-3.0`); https://docs.rs/slint/1.18.1/slint/docs/cargo_features/ ; https://docs.slint.dev/latest/docs/slint/guide/backends-and-renderers/backends_and_renderers/ and `.../backend_winit/` ; https://docs.slint.dev/latest/docs/rust/slint/fn.spawn_local.html ; https://github.com/slint-ui/slint/blob/master/LICENSE.md ; https://slint.dev/terms-and-conditions (Royalty-free Desktop, Mobile, and Web Applications License, version 2.0) ; https://slint.dev/pricing ; https://docs.rs/rfd/0.17.2/rfd/ and rfd 0.17.2 source/CHANGELOG (local crate source); interprocess 2.4.7 source (local crate source); GitHub issues via `gh` (slint-ui/slint #4069, #8592, #10912, #11931). Spike code and measurements are local. Accessed 2026-11-03.
- **Pinned mode**: We will use Slint 1.18.1 (`default-features = false`, features `std`, `compat-1-18`, `backend-winit` (+ `backend-winit-wayland`, `backend-winit-x11` on Linux), `renderer-software`, `accessibility`; **no** femtovg, no skia) as a separate settings executable that the daemon spawns on "Open settings", with `.slint` UI compiled by `slint-build`, `rfd` 0.17.2 `AsyncFileDialog::pick_folder()` awaited inside `slint::spawn_local` (Slint's own event loop drives the future; no extra executor), and a background `std::thread` running a tokio current-thread runtime that speaks newline-delimited JSON-RPC 2.0 over an `interprocess` 2.4.7 `local_socket` (Unix socket / Windows named pipe) to the daemon and pushes results into the UI with `Weak::upgrade_in_event_loop`, with inputs = settings model (folder pairs, checkboxes, bandwidth number, account state) and outputs = a native window with working Change/Remove buttons, OS-native folder dialog and live daemon status text, on Windows, Linux (Wayland and X11) and macOS. ## MVE — RustCrypto chacha20poly1305 0.11.0 `XChaCha20Poly1305` + aead-stream 0.6.0 `StreamBE32` in random-access chunk mode, per-blob key wrapped by an operator master key (server-side envelope encryption of blobs at rest)
- **Source**: https://crates.io/crates/chacha20poly1305 0.11.0 (2026-08-05), aead-stream 0.6.0 (2026-06-28, initial release), aead 0.6.1, aes-gcm 0.11.1 (2026-08-21), aes 0.9.4 (2026-11-02), aes-gcm-siv 0.12.1, ring 0.17.14 (2025-03-11), aws-lc-rs 1.19.0 (2026-10-28): READMEs, CHANGELOGs and `src/lib.rs` read from the downloaded crate sources; https://docs.rs/aws-lc-rs/1.19.0/aws_lc_rs/ ; https://github.com/briansmith/ring README; NIST SP 800-38D (https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf, sections 8.2.1 and 8.3, read from the PDF text); NCC Group "Public Report: RustCrypto AES-GCM and ChaCha20+Poly1305 Implementation Review" (published 2020-02-26, per web search; the report PDF itself could not be fetched, so audited versions are unverified); https://github.com/C2SP/C2SP/blob/main/age.md (age payload: 64 KiB chunks, 11-byte counter + 1-byte final flag); https://developers.google.com/tink/streaming-aead ; https://docs.docker.com/compose/how-tos/use-secrets/ ; https://docs.aws.amazon.com/kms/latest/APIReference/API_GenerateDataKey.html ; https://ryhl.io/blog/async-what-is-blocking/ . Benchmarks and spikes are local (`aeadbench`). Accessed 2026-11-03.
- **Pinned mode**: We will use `chacha20poly1305 =0.11.0` `XChaCha20Poly1305` with `aead-stream =0.6.0` `StreamBE32` (32-bit big-endian chunk counter and 1-byte final flag in the last 5 nonce bytes; 19-byte random per-blob nonce prefix) over fixed 64 KiB plaintext chunks (each stored as 64 KiB + 16-byte tag), using the primitive's random-access methods `StreamPrimitive::{encrypt_in_place, decrypt_in_place}(chunk_index, is_final, aad, buffer)`; a fresh random 256-bit data key per blob; a 9-byte blob header (format version = cipher+chunk size+construction, chunk-size exponent, 19-byte prefix) bound into every chunk's associated data together with the 16-byte blob ID; the data key wrapped with `XChaCha20Poly1305` under the operator master key (random 24-byte nonce, associated data = blob ID + master-key ID), stored in the PostgreSQL blob row in the same transaction as the commit; master key loaded from a file (default `/run/secrets/<name>` under Docker Compose) through a `MasterKey` trait with wrap/unwrap so a KMS implementation can be added later; with inputs = plaintext blocks (2 MiB uploads, out of order across up to 4 lanes) and HTTP Range requests, and outputs = ciphertext file at `blobs/<2hex>/<2hex>/<id>` of size 9 + plaintext + 16 x chunks, and plaintext slices for range reads and workers, on Linux x86-64 and aarch64 servers in Docker.
- **Inputs in the example**: spike `envelope`/`envelope_x` (4 chunks: 3 x 64 KiB + 1234 bytes): `EncryptorBE32::encrypt_next/encrypt_last` for the sequential path, `StreamBE32::from_aead(cipher, &prefix)` then `encrypt_in_place(i, last, aad, &mut Vec)` / `decrypt_in_place(i, last, aad, &mut Vec)` for random access; wrap via `encrypt_inout_detached` with blob ID as associated data.
- **Outputs in the example**: all checks passed for XChaCha20 (and for AES-256-GCM): round trip; random-access decrypt of chunk 2 and of the short final chunk (flagged final); treating a non-final chunk as final fails (truncation); chunk 1 presented as index 2 fails (reorder); wrong blob ID in associated data fails; one flipped bit fails; unwrap with a wrong blob ID fails. Full chunk = 65 552 bytes. Nonce prefix length: 19 B for XChaCha (24 - 5), 7 B for 12-byte-nonce AEADs.
- **Project inputs**: blobs up to 50 GiB (AC-4) uploaded as 2 MiB blocks (restrictions; the task text said 8 MiB, which does not match the restrictions file; the chunk layer works for any block size that is a multiple of 64 KiB), parallel lanes, resumable; reads with Range; transcode and thumbnail workers; scrub; backups.
- **Project outputs required**: stolen disk without master key yields no plaintext; rotation rewraps keys without rewriting blobs; range reads and downloads meet AC-2 (>= 90% of 1 Gbps, about 112 MB/s) (AC-43).
- **Match assessment**: exact match on function (spike); partial on maturity (new crate layout) and on API intent (random-access use of `StreamPrimitive` is a public trait method but not an advertised use case in the README).
- **If partial or mismatch**:
  - aead-stream README: "STREAM defends against reordering and truncation attacks ... and is proven to meet the security definition of 'nonce-based online authenticated encryption' (nOAE)"; the crate CHANGELOG says "0.6.0 (2026-06-28) - Initial release" (code extracted from `aead::stream`). Random access is a property of STREAM's per-chunk (counter, final-flag) nonce, and the spike exercised it, but the README documents only the sequential `Encryptor`/`Decryptor`.
  - Audit status: chacha20poly1305 and aes-gcm READMEs: "This crate has received one security audit by NCC Group, with no significant findings." aes-gcm-siv README: "No security audits of this crate have ever been performed." (only its AES and POLYVAL dependencies were covered). The NCC engagement was December 2019 (five person-days, two consultants) and covered the code of that date (web summary); the 0.11 line is a rewrite on `aead` 0.6 / `cipher` 0.5 / `aes` 0.9 (CHANGELOG), and `aes` 0.9.3 added VAES backends by default (2026-08-28), so the current versions are not the audited code. aead-stream as a separate crate has no audit; the vault's external review (v1.2) will cover the same construction. ring 0.17.14 was last published 2025-03-11 and its README says "We don't recommend that third parties depend upon it"; aws-lc-rs documents a `fips` feature ("Currently, aws-lc-fips-sys binds to AWS-LC-FIPS 4.x") and needs "a C/C++ compiler to build".
  - AES-GCM nonce limits, NIST SP 800-38D: section 8.3 "The following requirement applies to all implementations that use either 1) the deterministic construction with IVs whose length is not 96, or 2) the RBG-based construction, for IVs of any length. In other words, unless an implementation only uses 96-bit IVs that are generated by the deterministic construction: The total number of invocations of the authenticated encryption function shall not exceed 2^32 ...". Section 8.2.1: the IV is "the fixed field and the invocation field"; "the entire fixed field may consist of arbitrary bits when there is only one context to identify, such as when a fresh key is limited to a single session"; the invocation field "typically is either 1) an integer counter or ...". So a per-blob fresh key with a counter in the invocation field and 96-bit IVs is inside the deterministic construction and is not subject to the 2^32 random-IV cap; the cap matters only for the master-key wrap (one invocation per blob under one master key), which is why the wrap uses a 192-bit random nonce.
  - Tink streaming AEAD: "AES128_GCM_HKDF_1MB (or AES256_GCM_HKDF_1MB) is the faster option." and "AES128_GCM_HKDF_4KB consumes ~4 KB of memory and is a good choice if your system doesn't have a lot of memory."; "Partial plaintexts are obtainable without processing the entire ciphertext."; the nonce prefix is an "independent random 7-byte value". age: payload "split in chunks of 64 KiB". So 64 KiB is the established chunk size of an audited format and 1 MiB of a Google library; both are random-access capable.
  - Tokio guidance (Ryhl): "a good rule of thumb is no more than 10 to 100 microseconds between each `.await`"; for expensive CPU work he recommends rayon. At 1.16 GB/s one 64 KiB chunk costs about 56 us, one 1 MiB chunk about 900 us (measured end to end below), so 64 KiB chunks can be decrypted inline in the request task and 1 MiB chunks cannot.
  - Master key storage: Docker docs "Secrets are mounted as a file in `/run/secrets/<secret_name>` inside the container." and "If you're injecting passwords and API keys as environment variables, you risk unintentional information exposure." KMS: GenerateDataKey doc pattern "Store the encrypted data key (in the `CiphertextBlob` field of the response) with the encrypted data." and to decrypt "Use the Decrypt operation to decrypt the encrypted data key" (a per-read network call, so a KMS implementation needs an in-memory cache of unwrapped keys).

  Measured result differs from the aes-gcm-siv README ("Decryption performance is equivalent to AES-GCM. Encryption is marginally slower."): on this CPU GCM-SIV was faster than aes-gcm in both directions. End-to-end on page-cache-warm 1 GiB blobs (chunk read with `pread`, decrypt, no network; /tmp is tmpfs so this measures CPU and syscalls, not disk): XChaCha20 stream 1.16 GB/s at 64 KiB chunks and 1.25 GB/s at 1 MiB; AES-256-GCM stream 2.04 GB/s at both. Random 4 KiB range read (reads and decrypts the covering chunk): XChaCha 57 us (64 KiB) vs 860 us (1 MiB); AES-GCM 33 us vs 519 us. Tag overhead: 0.0244% at 64 KiB, 0.0015% at 1 MiB. A 50 GiB blob is 819 200 chunks at 64 KiB, far below the 2^32 counter limit (about 256 TiB).
- **Comparison and decision logic**:
  - AC-2 needs about 112 MB/s. Pinned mode decrypts at 1.16 GB/s (about 10% of one core per 112 MB/s stream; the 100-session aggregate of 1 Gbps = 125 MB/s costs about 11% of one core). Encrypt+`pwrite` measured 0.85 GB/s for XChaCha (includes filling the buffer), so uploads of 125 MB/s cost about 15% of a core.
  - The deciding fact is the no-hardware floor: aes-gcm without AES-NI/PCLMUL (soft backend) is 0.12 GB/s on this 3.8+ GHz core, which is about the AC-2 target on a fast desktop CPU and below it on a slower one (Raspberry Pi class, old Atom, CPUs without AES instructions, VMs masking them). ChaCha20-Poly1305 degrades gracefully (0.95 GB/s SSE2, 0.5 GB/s portable). The server is operator-installed on unknown hardware, so AES-GCM would add a hardware precondition for AC-2 that ChaCha does not have.
  - Pure Rust (RustCrypto) over ring/aws-lc-rs: ring/aws-lc-rs are 1.7x faster for AES-GCM on this CPU but add a C toolchain (aws-lc-rs) or a stale crate (ring), and the speed is not needed. Over AES-GCM-SIV: unaudited crate, two passes, and nonce-misuse resistance is moot with unique per-blob keys and counter nonces.
  - XChaCha20 vs ChaCha20 under `StreamBE32`: no measurable speed difference (1.32 vs 1.31 GB/s), and XChaCha gives the identical construction and type alias as the vault core (19-byte prefix), so one set of test vectors and one review covers both.
  - Upgrade path: the header's format version selects cipher and chunk size; a version 2 with AES-256-GCM (7-byte prefix) can be added for 10 GbE installs without rewriting version 1 blobs. Switch trigger: a measured crypto CPU share above 30% of the serving cores on the AC-1 test.
- **Design consequences (data path)**:
  - Upload: for each received block, verify BLAKE3 on plaintext, then encrypt its 32 chunks (2 MiB / 64 KiB) in place and `pwrite` at offset `9 + chunk_index x (65 536 + 16)`; blocks from parallel lanes are independent because chunk index is known from the block offset. The final-chunk flag requires the total size at session start; restrictions already reserve quota from the declared size, so a mismatch between declared and received size is a rejection. A zero-length blob is one empty final chunk (16-byte tag; to be tested). Acknowledge only after the batched `fdatasync` of the ciphertext (AC-38).
  - Download and Range: map the plaintext range to chunk indices, `pread` `(C + 16) x k` bytes, decrypt, slice. No whole-file pass. Memory per in-flight stream is one or a few 64 KiB buffers (1 MiB chunks would cost 16x more per request: 100 sessions would need 100 MB).
  - sendfile/zero-copy: the file bytes are ciphertext, so any kernel file-to-socket path or reverse-proxy file offload (X-Accel-Redirect style) would send ciphertext and is excluded. The server path in the restrictions (hand-built hyper accept loop in front of Caddy with buffering off) is already a userspace read-and-write path, so the loss is the theoretical sendfile gain only; nothing in AC-2 depends on it. (No measurement of sendfile vs read/write was made.)
  - Scrub (AC-24): read each blob sequentially and verify every chunk tag with the unwrapped key (needs the master key, so it runs inside the server binary as a throttled job). Tags authenticate every byte, the final flag detects truncation, and associated data binds the blob ID so a swapped file is detected. No separate stored checksum is needed; compare file size against the DB size as a cheap pre-check.
  - Workers (libvips/ffmpeg): tested on this host with ffmpeg 8.0.1: a 17 KB MP4 with `moov` at the end decoded from `pipe:0`, but a 35 MB MP4 with `moov` at the end produced 0 frames (error -22 Invalid argument) from `pipe:0` while the same file by path decoded 600 frames. So a pipe is not a correct universal path for video. Simplest correct path: the process that holds the master key decrypts the blob to a per-job scratch file (size-limited scratch volume, deleted after the job) and the decoder child gets that file read-only; the same path serves libvips. Recommended placement: decrypt in the API server and let the worker supervisor fetch the plaintext over an authenticated, job-scoped internal endpoint into its scratch dir, so the master key and the blob mount never leave the API host and remote workers (operator machines) need neither; derived outputs (thumbnails, transcodes) are written back through the same blob writer so they are encrypted too. This is a plan change to the "blob mount" wording for the supervisor (see findings).
  - Rotation: master keys have IDs; the wrapped-key record stores the ID; `sunnycloud keys rewrap` unwraps with an old key and wraps with the current one in short batched transactions (no blob I/O), idempotent and resumable; an old key can be retired only when no row and no retained DB backup still refer to it (a restored older backup carries old wrapped keys, so old master keys must be kept as long as such backups are kept). Rewrapping does not protect against an attacker who already holds both an old master key and old DB rows; rotating data keys would need blob rewrites and is out of scope.
  - Master key file: 32 random bytes (or base64), mode 0400, read at startup; refuse to start when missing, wrong length or world-readable; never log; Compose example with `secrets:` mounting `/run/secrets/sunnycloud_master_key`; env var supported only as `..._FILE` pointing to a path, not the key itself.

## Findings that change the plan
1. **Slint: ship the settings window with the software renderer only (no femtovg or skia in that binary).** On this NVIDIA + Wayland host the software build opens in about 50 ms and uses about 17 MB RSS with no environment variables; the GL path took 160-420 ms and 121-136 MB, and a simulated EGL failure ended in an error instead of falling back to software despite the docs saying it would. This is the only way to meet AC-16 "no environment-variable workarounds" with evidence. Windows and macOS cold starts are not measured: the 2019 HDD Windows laptop spike remains a gate, with the Tauri 2 triggers listed in the Slint block.
2. **Slint licence route: GPL-3.0-only** (no badge, compatible with AGPL through GPLv3 section 13). The royalty-free licence (AboutSlint widget or website badge) is a fallback only for a proprietary build. Add the GPL text for Slint to the third-party notices.
3. **Settings IPC security is not free:** the spike's Unix socket was created with the default umask (`srwxrwxr-x`). AC-48 needs explicit `mode(0o600)` plus a 0700 per-user directory, and a security descriptor on the Windows pipe (both APIs exist in interprocess 2.4.7); macOS needs its own 0700 directory (no `$XDG_RUNTIME_DIR`).
4. **rfd 0.17.2 changed on Linux:** its tokio/async-std features are gone, it uses `libdbus` (or zenity) for the XDG portal, and wlroots portals are unsupported. Document that Linux needs a portal backend or zenity for the native dialog (AC-17), and test GNOME, KDE and a wlroots compositor.
5. **Blob encryption: pin XChaCha20-Poly1305 with the STREAM chunk layer (not AES-GCM).** AES-256-GCM is 2x faster with AES-NI (2.4 vs 1.3 GB/s here) but without hardware AES it drops to 0.12 GB/s, which is about the AC-2 target; ChaCha stays at 0.5 GB/s even with no SIMD. Both clear 112 MB/s by 10x with hardware help. Chunk size 64 KiB (random 4 KiB read costs 57 us vs 860 us at 1 MiB, and decrypt can run inline without `spawn_blocking`). Upgrade path: the header version byte.
6. **Master-key lifecycle:** old master keys must be kept as long as any retained DB backup still holds wrapped keys under them; the restore test in AC-65 must include this case. The wrap uses a 192-bit random nonce so the 2^32 rule never applies to it.
7. **Workers and the blob mount:** a pipe is not a correct universal input for ffmpeg (35 MB MP4 with `moov` at the end: 0 frames from `pipe:0`, 600 frames from the file). Recommended path: decrypt in the API process and let worker supervisors fetch plaintext over an authenticated job-scoped internal endpoint into a per-job scratch file; then the master key and the blob store stay on the API host, remote workers need neither, and the decoder child gets only the scratch file. This changes the restrictions wording that the supervisor holds a blob mount; derived outputs (thumbnails, transcodes) must also be written through the encrypting blob writer. Needs the owner's decision.
8. **Block size inconsistency:** the task text for this round says 8 MiB upload blocks, restrictions.md says fixed 2 MiB blocks. The chunk layer is independent of it (any multiple of 64 KiB); confirm 2 MiB is current.

10. **iOS background uploads:** Apple supports only file-based uploads inside background URLSession sessions, executed by the system. The Rust loop only runs while the app process runs. If system-owned iOS background uploads are ever wanted, the core must be sans-IO; designing the core as a state machine now keeps that open.
