## MVE — RustCrypto chacha20poly1305 + aead-stream in XChaCha20Poly1305 / StreamBE32 chunked mode
- **Source**: https://crates.io/crates/chacha20poly1305 v0.11.0 (README, CHANGELOG, src/lib.rs); https://crates.io/crates/aead v0.6.1 (CHANGELOG, src/lib.rs); https://crates.io/crates/aead-stream v0.6.0 (README, src/lib.rs); https://doc.libsodium.org/secret-key_cryptography/secretstream and libsodium header `crypto_secretstream_xchacha20poly1305.h` (master, libsodium 1.0.22-RELEASE, 2026-04-09). Accessed 2026-11-02.
- **Pinned mode**: We will use `chacha20poly1305 =0.11.0` (`XChaCha20Poly1305`, default-features off, `alloc`) with `aead-stream =0.6.0` (`EncryptorBE32` / `DecryptorBE32`, `alloc`) with inputs 32-byte per-file key, 19-byte random per-file nonce prefix, plaintext chunks (64 KiB in the test), per-chunk AAD, and expect outputs ciphertext chunks of (chunk + 16 B tag) with the last chunk authenticated as final, on native Rust and wasm32-unknown-unknown.
- **Inputs in the example**: aead-stream README: "The STREAM construction supports encrypting/decrypting sequences of AEAD message segments, which is useful in cases where the overall message is too large to fit in a single buffer and needs to be processed incrementally." API: `encrypt_next(payload)`, `encrypt_last(payload)` (consumes the encryptor), `decrypt_next`, `decrypt_last`.
- **Outputs in the example**: Same README: "STREAM defends against reordering and truncation attacks ... and is proven to meet the security definition of 'nonce-based online authenticated encryption' (nOAE)". Source doc of `StreamBE32`: "Uses a 32-bit big endian counter and 1-byte 'last block' flag stored as the last 5-bytes of the AEAD nonce." (`NonceOverhead = U5`.) `StreamLE31`: "31-bit little endian counter and 1-bit 'last block' flag ... stored as the last 4 bytes of the AEAD nonce" (`NonceOverhead = U4`).
- **Project inputs**: files up to 100 MiB (AC-14), per-file key wrapped by the vault key, chunked, client-side in native, WASM and flutter_rust_bridge builds.
- **Project outputs required**: ciphertext only on the server; tampered, truncated, reordered or wrong-vault ciphertext rejected (AC-13).
- **Match assessment**: exact match on function; partial on packaging (dimension: crate layout changed).
- **If partial or mismatch**: aead 0.6.0 CHANGELOG, Removed: "`stream` module - extracted into `aead-stream` crate (#1801)"; chacha20poly1305 0.11.0 CHANGELOG, Removed: "`std` and `stream` features (#662)". So `chacha20poly1305::aead::stream` and the `stream` feature no longer exist; the dependency is the separate `aead-stream` crate, whose CHANGELOG says "0.6.0 (2026-06-28) - Initial release". Older tutorials and the candidate wording ("`aead::stream`") are stale.
- **Executed evidence** (scratchpad crate, release build, Linux x86-64; the same code compiled for wasm32-unknown-unknown with `--no-default-features`, 60 KB module with zero imports, and run in Node 22 / V8):
  - nonce sizes: XChaCha nonce is 24 B (chacha20poly1305 README: "extended 192-bit (24-byte) nonce"), so the BE32 per-file prefix is 24-5 = **19 B**; LE31 prefix is **20 B** (test passes `[u8;19]` / `[u8;20]`; type `Nonce<A,S> = Array<u8, NonceSize<A,S>>`).
  - 3 chunks + short last chunk (64 KiB chunks): round trip OK; each full chunk is 65 536 + 16 bytes.
  - dropping the final chunk: rejected. Swapping chunks 0 and 1: rejected. One flipped bit: rejected. Wrong key: rejected. Wrong prefix: rejected. A chunk appended after the final one: rejected.
  - counter limit: `encrypt_next` returns `Err` once `position == COUNTER_MAX` (u32::MAX for BE32); at 64 KiB that is far beyond 100 MiB.
  - gotchas found: (a) default features of chacha20poly1305 include `getrandom`, and `getrandom` 0.3 failed to compile for wasm32-unknown-unknown without a backend flag; with `default-features = false, features = ["alloc"]` and nonce/key generated by the host (JS `crypto.getRandomValues`) it builds. (b) The `Key` type alias is no longer generic (`chacha20poly1305::Key`, not `Key<XChaCha20Poly1305>`). (c) The in-place API takes `&mut dyn Buffer`; the `Vec` API needs `alloc`.
  - truncation caveat (design, not a bug): the decryptor must be told which chunk is last. The format must store the plaintext length or chunk count in the authenticated header (or read one chunk ahead until EOF); then the "last" flag authenticates the end.
- **Audit and platform status**: chacha20poly1305 README: "This crate has received one security audit by NCC Group, with no significant findings." The linked report is titled "Public Report: RustCrypto AES-GCM and ChaCha20Poly1305 Implementation Review", dated 2020-02-26 (archived 2020-06-06), so it covers an old version; whether XChaCha20Poly1305 was in its scope is not verified. **aead-stream has no stated audit** and is a 2026 initial release (the code is the former `aead::stream`, ~550 lines). The chacha20poly1305 README also says the portable implementation "is only constant time on processors which implement constant-time multiplication". no_std/WASM: aead-stream has `#![no_std]`; chacha20poly1305 `lib.rs` has `#![no_std]`; the RustCrypto/AEADs CI workflow `chacha20poly1305.yml` builds `--no-default-features` for `wasm32-unknown-unknown` and `thumbv7em-none-eabi`. Licence: MIT OR Apache-2.0 for all three.
- **Alternative: libsodium secretstream** (`crypto_secretstream_xchacha20poly1305`): libsodium docs: "Messages cannot be truncated, removed, reordered, duplicated or modified without this being detected"; header size = `crypto_aead_xchacha20poly1305_ietf_NPUBBYTES` = 24 B; per-message overhead `ABYTES = 1U + crypto_aead_xchacha20poly1305_ietf_ABYTES` = 17 B (tag byte is encrypted); tags MESSAGE/PUSH/REKEY/FINAL; "Rekeying happens automatically and transparently, before the internal counter of the underlying cipher wraps". It has a ready file example that fails on early FINAL or EOF without FINAL. Drawbacks for us: C library, needs a binding crate (`libsodium-sys-stable` 1.24.3, 2026-10-14; `sodiumoxide` 0.2.7 last release 2021-06-24, unmaintained) and a C toolchain for Android/iOS/WASM builds; the page does not mention WASM. Its wire format differs from STREAM, so the two are not interoperable. Advantage: audited, widely deployed, rekey and tags built in. For a single Rust core with one WASM build the RustCrypto stream is the simpler pick.
- **Restriction/AC binding**:

| Restriction or AC id | Pass / Fail / Verify / N/A | evidence |
|---|---|---|
| AC-13 tamper/truncate/reorder/wrong-key rejected | Pass | Executed test above (native); same assertions for truncation run in V8 wasm (`stream_check` = 7) |
| AC-13 server sees only ciphertext | Pass (by design) | Client-side encryption; output is chunk+16 B per chunk, random-looking |
| AC-14 100 MiB, larger rejected | Pass | Counter limit 2^32 chunks; size cap is policy; memory is per chunk (see block 3) |
| Restriction "chunked XChaCha20-Poly1305 per-file key" | Pass | Mode is exactly this; needs `aead-stream` dependency, not `aead::stream` |
| Audit status | Verify | chacha20poly1305: NCC audit 2020 (scope vs XChaCha unverified); aead-stream unaudited |
| AC-9, AC-19, AC-20, AC-21, AC-23 | N/A | not crypto-related |

  Rest of the AC/restriction list: N/A.
- **Proposed status**: Selected (RustCrypto `XChaCha20Poly1305` + `aead-stream` `EncryptorBE32`, pin exact versions, header carries format version, chunk size, prefix and total length; libsodium secretstream is the fallback if an audited primitive is required).

## MVE — argon2 crate in Argon2id (v0x13) / m=64 MiB, t=3, p=1 key-derivation mode
- **Source**: https://crates.io/crates/argon2 v0.6.0 (src/lib.rs, src/params.rs, Cargo.toml, README); https://www.rfc-editor.org/rfc/rfc9106 section 4; RustCrypto/password-hashes CI `argon2.yml` (raw GitHub). Accessed 2026-11-02.
- **Pinned mode**: We will use `argon2 =0.6.0` (`default-features = false, features = ["alloc"]`, no `parallel`) with `Argon2::new(Algorithm::Argon2id, Version::V0x13, Params::new(65536, 3, 1, Some(32)))` and `hash_password_into(passphrase, salt16, &mut key32)` with inputs passphrase bytes and a 16-byte random salt, and expect a 32-byte key on native and wasm32-unknown-unknown (in a Web Worker).
- **Inputs in the example**: lib.rs "Key Derivation" section: "This API is useful for transforming a password into cryptographic keys for e.g. password-based encryption"; example calls `Argon2::default().hash_password_into(password, salt, &mut output_key_material)` with a 32-byte output. Params doc: `m_cost` "memory size in 1 KiB blocks", `t_cost` "number of iterations", `p_cost` "degree of parallelism".
- **Outputs in the example**: 32 bytes of key material ("Can be any desired size").
- **Project inputs**: passphrase (UTF-8 bytes), per-vault random salt, parameters read back from the vault header.
- **Project outputs required**: 32-byte vault key-encryption key; parameters (version, m, t, p, salt) serialized in the vault header; same key on web, mobile and desktop.
- **Match assessment**: exact match.
- **If partial or mismatch**: not needed. Notes: (1) The PHC-string API (`password-hash` feature) is documented for authentication hashes ("Do not use this API to derive cryptographic keys"); for the vault use `hash_password_into` and serialize `m_cost()/t_cost()/p_cost()` and the version ourselves in the header. (2) RFC 9106 section 4 gives the SECOND RECOMMENDED option as "Argon2id with t=3 iterations, p=4 lanes, m=2^(16) (64 MiB of RAM), 128-bit salt, and 256-bit tag size"; our p=1 differs from the RFC's p=4 (same memory and passes; lanes only change parallelism and slightly the cost model), which is defensible for WASM without threads but should be recorded as a deliberate deviation. 16-byte salt matches "16 bytes is RECOMMENDED".
- **Executed evidence**: native release build on AMD Ryzen 9 3900XT: 128 ms for m=65536, t=3, p=1. The wasm32-unknown-unknown build (module imports: none) run in Node 22.23 (V8, same engine as Chrome): about 190-203 ms; wasm linear memory grew from 1.1 MiB to 65.2 MiB in one call (so `memory.grow` is used and a 64 MiB reservation is enough). This is a desktop CPU, not a browser or a phone; low-end phones are likely several times slower (not measured, Verify). No threads are needed at p=1; the `parallel` feature pulls in `rayon` and is off by default.
- **Platform status**: README: "Support is provided for embedded (i.e. `no_std`) environments, including ones without `alloc` support." The upstream CI builds argon2 for `wasm32-unknown-unknown` and `thumbv7em-none-eabi`. No audit is stated in the crate README or the password-hashes repo README (grep for "audit" returned nothing): treat as unaudited, but it is a long-used implementation of a specified algorithm (RFC 9106 test vectors exist in the repo, not re-checked here). Licence MIT OR Apache-2.0. 0.6.0 stable was released 2026-08-27 after rc.1 to rc.8 (the 0.5 to 0.6 move changed the `password-hash` API: `PasswordHash` is now `password_hash::phc::PasswordHash`).

## MVE — RFC 8628 device authorization grant implemented server-side in our axum API (no library), opaque tokens stored as SHA-256 hashes in PostgreSQL
- **Source**: https://www.rfc-editor.org/rfc/rfc8628.txt (sections 3.2, 3.4, 3.5, 5.1, 5.2, 6.1); https://www.rfc-editor.org/rfc/rfc6819.txt (5.1.4.1.3, 5.1.4.2.2); https://www.rfc-editor.org/rfc/rfc9700.txt (refresh-token rotation); crates.io searches ("rfc8628", "device authorization grant", "oauth2 server", "oidc provider") on 2026-11-02; crates `oauth-as` 1.0.1 (2026-11-02), `cratefield-module-device-auth` 0.3.3, `oauth-device-flows` 0.1.0, `oxide-auth` 0.6.1 (src/README); PostgreSQL 18 docs (binary string functions). Accessed 2026-11-02/03.
- **Pinned mode**: We will implement in our own code the RFC 8628 server role (device authorization endpoint, verification page behind a browser session, token endpoint polling) with inputs desktop-daemon `client_id` (public client, no secret) and the signed-in browser session, and expect outputs `device_code` (>=256 random bits), `user_code` (8 letters from `BCDFGHJKLMNPQRSTVWXZ`), `interval`, `expires_in`, then opaque access and refresh tokens, on axum 0.8 / tokio / PostgreSQL 18, with the device token later stored by the daemon in the OS keychain.
- **Inputs in the example**: RFC 8628 3.2 response: `device_code` REQUIRED, `user_code` REQUIRED, `verification_uri` REQUIRED ("short and easy to remember"), `verification_uri_complete` OPTIONAL, `expires_in` REQUIRED ("lifetime in seconds of the device_code and user_code"), `interval` OPTIONAL ("The minimum amount of time in seconds that the client SHOULD wait between polling requests ... If no value is provided, clients MUST use 5 as the default"). Example in the RFC: `WDJB-MJHT`, `expires_in` 1800, `interval` 5.
- **Outputs in the example**: token endpoint errors defined in 3.5: `authorization_pending`, `slow_down` ("the interval MUST be increased by 5 seconds for this and all subsequent requests"), `access_denied`, `expired_token`; "If the client receives an error response with any other error code, it MUST stop polling".
- **Project inputs / outputs required**: AC-20 (device code voided after 5 wrong attempts; 429 + Retry-After per code, account, IP), AC-21 (revocation within 5 s), restriction (device tokens in OS keychain; Apple has no device flow, so our own grant).
- **Match assessment**: exact match to the spec; no maintained library is needed or recommended (hand-written).
- **Spec requirements to implement (verbatim anchors)**:
  - User code format, 6.1: base-20 set "BCDFGHJKLMNPQRSTVWXZ" ("Further removing vowels to avoid randomly creating words"); "WDJB-MJHT" has 8 significant characters, "The resulting entropy is 20^8"; "the server should strip dashes and other punctuation"; "the user's input should be uppercased before a comparison"; avoid confusable characters.
  - Brute force, 5.1: "it is recommended that the server rate-limit user code attempts"; "one uses an 8-character base 20 user code (with roughly 34.5 bits of entropy), the rate-limiting interval and validity period would need to only allow 5 attempts in order to get the same 2^-32 probability of success". This matches our AC-20 rule (void after 5 wrong attempts) and the 8-letter code.
  - Device code, 5.2: "a very high entropy code SHOULD be used".
  - Polling, 3.5: client "MUST wait at least the number of seconds specified by the 'interval' parameter ... or 5 seconds if none was provided"; on connection timeouts clients "MUST unilaterally reduce their polling frequency"; exponential backoff "RECOMMENDED". The RFC states no server-side limit on poll rate beyond `slow_down`, so the server should answer `slow_down` for polls faster than `interval`, and 429 for abuse (AC-20 behaviour is our addition).
  - Remote phishing, 5.4: "RECOMMENDED to inform the user that they are authorizing a device during the user-interaction step ... The authorization server SHOULD display information about the device" (show device name and OS on the approval page).
  - Public clients: the token request needs no secret ("If the client was issued client credentials ... MUST authenticate"; the daemon has none).
- **Existing Rust crates (server side)**: `oauth-as` 1.0.1 describes itself as "An embeddable OAuth 2.1 Authorization Server library ... a full device-authorization-grant state machine, and a storage trait the host implements", licence MIT OR Apache-2.0, about 51k downloads. Facts that matter: repo MattJackson/oauth-as created 2026-08-08, 9 stars, one maintainer, 1.0.0 on 2026-09-24 (about six weeks before today); its README certification claims ("OpenID Certified", "independent conformance 8/8") are the author's own and were not independently verified here; the README itself says the host must "sweep expired records on a timer", "Rate limit", "Wire the CSRF seam". It would bring an OAuth 2.1 AS surface (DPoP, mTLS, PAR, RAR, FAPI) we do not need, a Storage trait to implement over Postgres, and a young single-maintainer dependency in the auth path. `oxide-auth` 0.6.1 (2024-06-02, RFC 6749 server for web frameworks) has no device grant in its description. `cratefield-module-device-auth` is a module of a private framework (573 downloads). `oauth-device-flows` and openidconnect/oauth2 (README: "OAuth 2.0 Device Authorization Grant") are client-side. Conclusion: no mature maintained server-side RFC 8628 crate; hand-write (about 200 lines plus tables), using `oauth-as` only as a reading reference or a test oracle. Not verified: that `oauth-as` compiles with our axum/tokio versions.
- **Opaque tokens hashed at rest**: RFC 6819 5.1.4.1.3: "The authorization server should not store credentials in clear text. Typical approaches are to store hashes instead or to encrypt credentials. If the credential lacks a reasonable entropy level (because it is a user password), an additional salt will harden the storage"; 5.1.4.2.2: "The token value should be >=128 bits long and constructed from a cryptographically strong random or pseudo-random number sequence". The RFC does not name a hash. Because our tokens are 256-bit random, an unsalted fast hash is enough, so **SHA-256 of the raw token** (stored as `bytea`, unique index, lookup by hash; no constant-time compare needed because the DB matches on the hash) is the choice (our inference from the two RFC sentences). PostgreSQL provides `sha256(bytea)` natively (PG docs, binary string functions), so a SQL-only lookup is possible; Rust side use the `sha2` crate or the `blake3` already in the project (BLAKE3 would also satisfy the same reasoning, but SHA-256 keeps SQL parity). Do not use Argon2 for tokens (no benefit with 256-bit entropy, high CPU on a hot path). Refresh rotation: RFC 9700: "Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation as described in Section 4.14" (desktop daemons and the mobile app are public clients, so rotation with reuse detection applies).

|---|---|---|

These are unverified community reports, not Apple statements. Treat as **Needs user decision** after a device spike.
  - Request body (Immich limitation 2, same thread): "the body of the HTTP request can only contain the asset data itself", so no multipart; metadata goes in the URL and headers (the destination `URLRequest` carries "authentication headers, and any metadata needed"). Our server needs a raw-body ingest route that is separate from the 2 MiB block protocol (one job = one `PHAssetResource`; a Live Photo or edited photo is several resources).
  - Draft protocol: Apple article: "The background upload system supports resumable uploads according to the draft [draft-ietf-httpbis-resumable-upload] protocol." **Apple does not name a draft revision or interop version** in that article. Server requirements from the article: before an upload the system "sends an HTTP `OPTIONS` request to your upload endpoint"; the server answers "`200 (OK)` status code and include the `Upload-Limit` header field", or "`501 (Not Implemented)`" if unsupported (the system caches this); "For each upload, your server must also provide in-band feature detection by sending a `104 (Upload Resumption Supported)` informational response while the client uploads the request body", with `Location` set to the upload URL; "Your API must include both the `OPTIONS` preflight check and the `104` informational response." Developer Mode (iOS 27 only) removes the extension runtime limit for testing.
  - Which draft: the draft now at revision 15 (2026-11-02) has interop version **10** (Appendix B: "The current interop version is 10"); servers MUST NOT send 104 unless the request's `Upload-Draft-Interop-Version` matches and must echo it on the 104. The tus/rufh table lists URLSession at interop 3 (draft -01, iOS 17.x), 5 (iOS 18.0), 6 (draft -04/-05, since iOS 18.1); Apple's own Foundation page still cites "draft-ietf-httpbis-resumable-upload-01.txt". Draft -04 added "Allow client to fetch upload limits upfront via OPTIONS" and -04/-05 are where OPTIONS + `Upload-Limit` exist, which is consistent with the extension needing at least interop 6, but the actual interop value sent by iOS 26.1/27 is unverified: capture it on a device. The server must accept a configurable set of interop versions (at least 6, ideally also 10).
  - Server cannot be plain axum for the 104: hyper 1.12.0 source (`src/proto/h1/role.rs`): "hyper currently doesn't support returning 1xx status codes as a Response. This is because Service only allows returning a single Response", and a 1xx response is turned into a 500 (`new_user_unsupported_status_code`: "response has 1xx status code, not supported by server"). Server-side informational responses are still open work in hyper (issue #2426 "Ideas for supporting HTTP Early Hints server-side", #3815 "prototype support for 1xx informational responses", #4114 "HTTP/2 103 Early Hints Support"). The lower-level `h2` 0.4.20 crate does have server `send_informational_headers`, so the ingest endpoint could be written directly on `h2` (or on a patched hyper), or fronted by a component that already speaks the draft (Apple's SwiftNIO `NIOResumableUpload` example, or tusd in Go with "experimental support for the draft"); no Rust crate implementing the draft server side was found (crates.io search "rufh", "resumable upload http draft": only tus-protocol crates, which are a different protocol). Whether a reverse proxy in front forwards 1xx interim responses and the `Upload-*` headers unbuffered is also Verify (the restrictions already require no request buffering).
- **Executed evidence**: none (no iOS 26.1 device used; only documentation and sources read).

## Findings that change the plan
1. **`aead::stream` no longer exists.** aead 0.6.0 (2026-06-08) removed it and chacha20poly1305 0.11.0 (2026-06-28) removed its `stream` feature; use the new `aead-stream` 0.6.0 crate (initial release 2026-06-28, unaudited). Executed tests confirm BE32 (19-byte XChaCha prefix, 5 bytes of counter+flag), truncation, reorder, bit-flip, wrong key and appended chunk are all rejected. Any doc or tutorial citing `chacha20poly1305::aead::stream` is stale. Pin exact versions; libsodium secretstream stays the audited fallback.
2. **WASM build pitfall:** chacha20poly1305's default `getrandom` feature broke the wasm32-unknown-unknown build (getrandom 0.3 needs a backend). Build the core with `default-features = false`, `alloc`, and pass random bytes from the host (JS `crypto.getRandomValues`, platform RNG in frb). With that, the whole core (stream + Argon2id) is a 60 KB module with no imports; Argon2id m=64 MiB t=3 p=1 took about 200 ms in V8 on a desktop Ryzen (128 ms native); low-end phones and Safari are unmeasured.
3. **Argon2 is p=1 here vs RFC 9106's p=4 for the same 64 MiB / t=3 option**; record it as a deliberate deviation, store (version, m, t, p, salt) in the vault header, and benchmark phones before freezing.
4. **Rust-to-WASM toolchain moved:** the rustwasm org was sunset in 2025; use github.com/wasm-bindgen/wasm-bindgen (0.2.130) and github.com/wasm-bindgen/wasm-pack (0.15.1). wasm-bindgen's guide names only webpack (and Rolldown with a plugin) as known-compatible bundlers, so the Vite + SvelteKit path needs a spike (`--target web`, module Worker, single-threaded; threads would need nightly, atomics and COOP/COEP headers and are not needed).
5. **flutter_rust_bridge:** stable is 2.13.0, newest is 2.14.0-beta.2; Cargokit (default) is archived upstream (frb keeps its own fork) and Native Assets is the future backend. Google Play requires 16 KB page support for apps targeting API 35+ with enforcement from 2027-02-01 (NDK r28+ is aligned by default), so the Rust `.so` needs an alignment check in CI. frb's own web mode is not used.
6. **Auth:** openidconnect 4.1.0 depends on oauth2 5.0.0 (last release 2025-01-21); jsonwebtoken needs a crypto-backend feature and 11.x is a fresh breaking release. Apple documents no PKCE and its discovery doc has no `code_challenge_methods_supported`, only `client_secret_post` and RS256, so Apple is a confidential-client flow. Request no Apple scopes so `response_mode=query` works and no `form_post` route or first-login-only `user` JSON handling is needed (identity is `sub`). GitHub PKCE is supported (S256 only); Facebook PKCE and the token-exchange method (documented as GET) are unverified.
7. **RFC 8628 server side:** no mature Rust server crate exists. The only fully featured one found, `oauth-as` 1.0.1, is six weeks past 1.0 with a single maintainer and self-reported certification; hand-write it. RFC 8628 5.1's own example (8-character base-20 code, 5 attempts) matches AC-20's "void after 5 wrong attempts". Store SHA-256 of 256-bit random tokens.
8. **Google Play bans the obvious Android design for automatic backup:** Play's foreground-service policy for dataSync says the backup review video "cannot show fully automatic or background backup or recovery". Native WorkManager with a MediaStore trigger is the compliant route; AC-9's 60 s has no documented latency and needs device measurement. Android 14+ "Select photos" access expires, so full access must be requested and checked.
9. **iOS background upload has two real blockers for a self-hosted product:** (a) `BackgroundUploadURLBase` is a static Info.plist string and Apple's docs do not say whether per-user destinations are allowed (community reports say the system only uses it for connectivity validation, unconfirmed); (b) Apple requires the server to send a `104` interim response, and hyper 1.12.0 (so axum) cannot send 1xx responses (open hyper issues #2426, #3815, #4114). The 104 endpoint must be built on `h2` directly, or on a draft-aware front, and must tolerate the `Upload-Draft-Interop-Version` the device sends (draft is at revision 15, interop 10; iOS versions seen use 3 to 6; Apple does not name its draft). Body is raw asset bytes only, one job per `PHAssetResource`. The extension class is deprecated in iOS 27 in favour of `PHBackgroundResourceUploadJobExtension`, so the Swift target needs both.
10. **App Store 4.8 conflicts with "operator may enable any subset" (AC-19)** on iOS: the iOS app cannot show Google/Facebook/GitHub login without an equivalent option such as Sign in with Apple. Needs a decision (default recommendation: iOS shows other social providers only when Apple is also configured). Guidelines were last updated 2026-10-16.
11. **Licences:** all Rust crates above are MIT or Apache-2.0 (dual); flutter_rust_bridge MIT; photo_manager Apache-2.0; background_downloader BSD-3-Clause text (GitHub reports NOASSERTION); the workmanager plugin repo has no licence file detected by the GitHub API (check before use). No GPL or paid dependency introduced by this card.

*Not verified anywhere in this card (needs a spike): browser/phone/Safari Argon2 timings; Vite + SvelteKit + wasm-bindgen glue; a 100 MiB end-to-end web and mobile run; frb Android/iOS builds and FFI copy cost; every provider flow against live apps (Facebook especially); Android 60 s latency per OEM; the iOS interop version and the destination-URL rule on a real iOS 26.1+ device; whether the reverse proxy forwards 1xx and `Upload-*` unbuffered.*
