# MVE fact cards: server and media lead candidates

Accessed 2026-11-02/03. Versions are those shown on docs.rs / crates.io (crates.io API) on that date. "Restr:" names a bullet of `_docs/00_problem/restrictions.md` (they have no ids). Claims I could not verify are marked VERIFY, never assumed.

## MVE — axum + hyper + hyper-util + tokio in streaming-upload mode
- **Source**: docs.rs axum 0.8.9 (crates.io updated 2026-04-14); hyper 1.12.0; hyper-util 0.1.21; tokio 1.54.1; tower-http 0.7.1; axum source `axum/src/serve/mod.rs` (main); axum examples `serve-with-hyper`, `graceful-shutdown`. Accessed 2026-11-02.
- **Pinned mode**: We will use axum 0.8 with a hand-built accept loop (`hyper_util::server::conn::auto::Builder`, as in axum's `serve-with-hyper` example) so the HTTP/2 window sizes can be set, with inputs `Request<Body>` handled as `body.into_data_stream()` written straight to a pre-sized staging file, and expect outputs "file on disk, hash result, 2xx/4xx" on tokio multi-thread, plain h2c/HTTP/1.1 behind a TLS-terminating reverse proxy (or hyper TLS acceptor, not verified here).
- **Inputs in the example**: `Body::into_data_stream` ("Convert the body into a `Stream` of data frames"; trailers are discarded); `DefaultBodyLimit` doc; `tower_http::limit::RequestBodyLimitLayer`; `hyper_util ... auto::Http2Builder::{initial_stream_window_size, initial_connection_window_size, adaptive_window, max_frame_size, max_concurrent_streams}`; `with_graceful_shutdown`; `tower_http::services::ServeDir/ServeFile`.
- **Outputs in the example**: streaming handler without buffering; 413 on over-limit; h2 settings applied per connection; server future resolving after all connections end; 206/416 range responses.
- **Project inputs**: 2 MiB sync blocks (up to 4 lanes) and, for the IETF resumable-upload draft (iOS), one PATCH-like body up to 50 GiB; 1 Gbps at RTT <= 20 ms; downloads with Range.
- **Project outputs required**: AC-2 >= 90% of link; AC-3 resume <= 10 MiB; AC-4 50 GiB with O(1) finish; AC-21 live streams cut within 5 s; graceful restart without losing accepted blocks.
- **Match assessment**: partial. Streaming, body limits, graceful shutdown and Range are all present; the default HTTP/2 flow-control windows are too small for the AC-2 target, and `axum::serve` does not expose them.
- **If partial or mismatch**:
  - Windows: hyper source `src/proto/h2/server.rs` sets `const DEFAULT_CONN_WINDOW: u32 = 1024 * 1024;` and `const DEFAULT_STREAM_WINDOW: u32 = 1024 * 1024;`, and `adaptive_window` defaults to `false`. Analysis (ours, not a quote): bandwidth-delay product at 1 Gbps x 20 ms = 2.5 MB, and the 1 MiB connection window caps all streams together at about 1 MiB / 0.02 s = 52 MB/s (about 420 Mbit/s), below 90%. So both `initial_connection_window_size` and `initial_stream_window_size` must be raised (4 MiB or more) or `adaptive_window(true)` used (doc: enabling it "overrides" the initial window sizes). This is only the axum-to-proxy hop if a proxy terminates TLS; the client-facing window is then the proxy's setting (VERIFY per proxy, not researched here).
  - `axum::serve` docs say nothing about HTTP/2 configuration or TLS; hyper-util's `auto::Builder::http2()` ("Http2 configuration") is the documented route. axum does not terminate TLS itself in the docs I read.
  - Body limits: `DefaultBodyLimit` docs: "For security reasons, Bytes will, by default, not accept bodies larger than 2MB" and, when an extractor reads the body directly (`Body::poll_frame`), "the default limit is not applied". So a streaming handler is unlimited unless we add `RequestBodyLimitLayer`. tower-http source (`limit/service.rs`): `Content-Length` above the limit returns 413 before the handler runs; otherwise the body is wrapped in `http_body_util::Limited`, so a chunked/lying body fails mid-stream as a body error, not as a 413. Use a per-route layer: about 2 MiB plus slack on the block route, 50 GiB + slack only on the resumable-upload route.
  - Graceful shutdown: axum source: after the signal it stops accepting, calls hyper `graceful_shutdown()` on each connection, and returns "only once every connection task has ended"; it has no timeout of its own. A 50 GiB upload therefore blocks shutdown; we need our own drain deadline (axum example uses `TimeoutLayer` with the comment "Graceful shutdown will wait for outstanding requests to complete. Add a timeout so requests don't hang forever."). Interrupted uploads are covered by AC-3 resume.
  - Range: tower-http `ServeDir` docs: `ignore_multi_range_requests` "Configure whether syntactically valid multi-range requests should be ignored"; "Malformed range headers and unsatisfiable single-range requests still result in `416 Range Not Satisfiable`"; source `open_file.rs` parses with `http_range_header`. The docs I read do not state "206" for a satisfiable range in prose (VERIFY with a test). Blobs are `blobs/<2hex>/<2hex>/<uuid>`, so a custom handler using `ServeFile` per resolved path (after the DB/ACL check) is needed, not `ServeDir` on the tree.
- **Restriction/AC binding**:

| Restriction or AC id | Pass / Fail / Verify / N/A | evidence |
|---|---|---|
| Restr: Server on axum and tokio | Pass | axum 0.8.9 current on crates.io; sqlx 0.9 and apalis-postgres 1.0.0 also on tokio |
| AC-2 (>= 90% of 1 Gbps) | Verify | default 1 MiB windows too small at 20 ms RTT (see above); needs window tuning plus a load test; proxy hop VERIFY |
| AC-3 (resume <= 10 MiB) | Pass (design) | 2 MiB blocks x 4 lanes = 8 MiB; streaming handler can fsync then ack per block |
| AC-4 (50 GiB, O(1) finish) | Verify | streaming to a staging file is supported; per-route 50 GiB limit and proxy body-size limits need a test |
| AC-21 (stream cut <= 5 s) | Verify | graceful shutdown waits for connections; per-session cancellation must be our own code |
| Restr: reverse proxy must not buffer | N/A to axum | proxy configuration; not axum-verifiable |
| AC-25, AC-10, AC-11, AC-28 | N/A | media side |

  Other ACs and restrictions are N/A for this candidate.
- **Proposed status**: Selected (with the manual hyper-util accept loop and explicit window settings; both are mandatory, not optional).

## MVE — sqlx 0.9 with PostgreSQL 18 in runtime-tokio + rustls mode
- **Source**: docs.rs sqlx 0.9.0 (changelog "0.9.0 - 2026-05-06", crates.io updated 2026-05-21); sqlx `README.md`, `sqlx-cli/README.md`, `CHANGELOG.md`, `.github/workflows/sqlx.yml`, `sqlx-core/src/pool/options.rs` (main); PostgreSQL 18 docs `sql-select` and `ddl-rowsecurity`. Accessed 2026-11-02.
- **Pinned mode**: We will use sqlx 0.9 (features `runtime-tokio`, `tls-rustls-ring-webpki` or `tls-rustls-aws-lc-rs`, `postgres`, `macros`, `migrate`, `json`, `uuid`, `chrono` or `time`) with inputs SQL strings checked at compile time through `query!`/`query_as!` plus `cargo sqlx prepare` offline metadata, and expect outputs typed rows, embedded migrations, `PgListener` notifications and `FOR UPDATE SKIP LOCKED` job claims, on PostgreSQL 18.
- **Inputs in the example**: README feature list; `sqlx::migrate!` ("Embeds migrations into the binary by expanding to a static instance of `Migrator`"); `PgListener`; pool defaults from source; `sqlx-cli` offline mode.
- **Outputs in the example**: compile-time checked queries, embedded migrations, LISTEN/NOTIFY with auto-reconnect, bounded pool.
- **Project inputs**: PostgreSQL 18; 500 users, about 25M rows; per-account commit order; held long-poll on an account cursor; job queue on SKIP LOCKED.
- **Project outputs required**: AC-6 listing 10,000 entries <= 300 ms p95 (paged); AC-5/AC-21 change notification; AC-27 deletion; short transactions (coderule).
- **Match assessment**: partial. Everything required is present except that PostgreSQL 18 is not in sqlx's own CI matrix.
- **If partial or mismatch**:
  - CI: `.github/workflows/sqlx.yml` on main lists `postgres: [ 17, 13 ]`; PostgreSQL 18 is not tested upstream. The wire protocol is unchanged for default clients, but I did not find an official statement of PG 18 support: VERIFY in our own CI against a PG 18 container.
  - Notifications are lossy: `PgListener` docs: "As notifications are transient, any received while the connection was lost, will not be returned." So LISTEN/NOTIFY is a wake-up hint only; the durable source is the per-account cursor in a table (matches the long-poll design). The listener "will auto-reconnect" and re-subscribes to all channels; `eager_reconnect` defaults to reconnecting before returning `Ok(None)` from `try_recv`.
  - MSRV: changelog: "the supported Rust version for this release cycle is 1.94.0". `Cargo.lock` is no longer tracked upstream; `cargo install --locked sqlx-cli` no longer works. Query functions take `impl SqlSafeStr` (only `&'static str` or `AssertSqlSafe`), which is a guard against `format!` SQL.
  - Offline mode: `sqlx-cli/README.md`: "Save query metadata for offline usage: `cargo sqlx prepare`"; "The presence of a `DATABASE_URL` environment variable will take precedence over the presence of `.sqlx`"; set `SQLX_OFFLINE=true` to force offline. In CI run `cargo sqlx prepare --check`.
  - Pool defaults (source): `max_connections: 10`, `min_connections: 0`, `acquire_timeout` 30 s, `idle_timeout` 10 min, `max_lifetime` 30 min, `test_before_acquire` "Defaults to `true`". Each `PgListener::connect` takes its own connection outside the pool unless built from a pool.
  - SKIP LOCKED: PostgreSQL 18 docs, SELECT, Locking Clause: "With `SKIP LOCKED`, any selected rows that cannot be immediately locked are skipped. Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table." It is plain SQL, so sqlx passes it through; no sqlx-specific doc was needed.
  - Row-level security: sqlx has no RLS API and no doc on it; it is ordinary SQL. PG 18 docs: "Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system" and "Table owners normally bypass row security as well, though a table owner can choose to be subject to row security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`." Through a pool, the policy variable would have to be set per transaction (`set_config(..., true)` inside `pool.begin()`); that pattern is mine, not from sqlx docs (VERIFY by test). The app must connect as a role that is neither owner nor BYPASSRLS. Not required by the restrictions; recommended only as defence in depth.
- **Restriction/AC binding**:

|---|---|---|

| Restr: Postgres job queue, no Redis | Pass | SKIP LOCKED documented in PG 18 SELECT docs |
| Restr: held long-poll on per-account cursor | Pass | `PgListener` as wake-up, cursor table as truth (notifications can be lost) |
| AC-6 (list 10,000 <= 300 ms) | Verify | needs a measurement; sqlx offers `fetch` streaming and keyset paging |
| AC-5, AC-21 | Verify | LISTEN/NOTIFY wake-up latency is not documented; test |
| AC-27 | N/A to library | SQL `ON DELETE CASCADE` design |
| Restr: API documented with OpenAPI | N/A | not sqlx |

## MVE — blake3 crate in streaming Hasher mode (single-threaded per block, rayon optional)
- **Source**: docs.rs blake3 1.8.7 (crates.io updated 2026-08-20), `Hasher`, `hazmat` module, crate features; github.com/oconnor663/bao README; crates.io `bao` 0.13.1 (2025-04-07), `bao-tree` 0.17.0 (2026-10-22). Accessed 2026-11-02.
- **Pinned mode**: We will use blake3 1.8.x with `Hasher::update` called on each received buffer (default features, no rayon on the request path), and expect outputs a 32-byte `Hash` per 2 MiB block and per file, on tokio (hashing in the streaming handler, or in `spawn_blocking` for the scrub).
- **Inputs in the example**: `Hasher::update` ("Add input bytes to the hash state. You can call this any number of times."); `finalize` ("idempotent"); `update_rayon`; `update_mmap(_rayon)`.
- **Outputs in the example**: an incrementally computed `Hash` equal to `blake3::hash` of the whole input.
- **Project inputs**: bytes arriving in order within a block; up to 4 blocks in flight; whole files up to 50 GiB for the scrub.
- **Project outputs required**: AC-7 end-to-end verification; AC-24 scrub; AC-2 hashing must not cap throughput.
- **Match assessment**: exact match for per-block streaming; partial for the whole-file hash over parallel out-of-order blocks.
- **If partial or mismatch**:
  - Rayon: `update_rayon`: "As a rule of thumb on x86_64, update_rayon is slower than update for inputs under 128 KiB"; feature "disabled by default"; "even if this feature is enabled, all other APIs remain single-threaded". The `update_mmap_rayon` doc warns that multithreading can hurt, for example with large files on spinning disks. Use rayon only in the scrub of large blobs (`rayon` + `mmap` features) if disk allows; calling it on a tokio worker thread would block, so run it in `spawn_blocking`.
  - Whole-file hash from independently hashed blocks: `blake3::hazmat` is "for projects like Bao, which work directly with the interior hashes"; it offers `set_input_offset`, `finalize_non_root`, `merge_subtrees_non_root`, `merge_subtrees_root`, and warns "merge functions can't detect shape mistakes" so results must be checked against `blake3::hash`. 2 MiB blocks aligned at 2 MiB multiples are power-of-two subtrees, so a whole-file root can be merged from per-block chaining values; this is optional and must be tested. Simpler: define the file identity as the hash of the ordered block-hash list (no hazmat).
  - Bao / verified streaming: Bao README: "an implementation of BLAKE3 verified streaming", with slice extraction and outboard mode; "Bao is beta cryptography software. It has not been formally audited yet." `bao` crate 0.13.1 was last updated 2025-04; `bao-tree` 0.17.0 (n0-computer, "with custom chunk groups and range set queries") is active (2026-10-22). Not needed in v1, since 2 MiB blocks are already the verification unit; relevant later for Range-verified downloads.
- **Restriction/AC binding**:

| Restriction or AC id | Pass / Fail / Verify / N/A | evidence |
|---|---|---|
| Restr: BLAKE3 hashing | Pass | `Hasher::update` any number of calls |
| AC-7 end-to-end hash | Pass | client and server compute the same `Hash` per block |
| AC-24 scrub | Pass / Verify | `update_mmap_rayon` exists; throttling is our code; HDD caveat in docs |
| AC-2 | Pass (analysis in `00_ac_assessment.md` figure of about 2.85 GB/s single thread; not re-measured here) | VERIFY with a benchmark on the target CPU |
| AC-13 vault | N/A | vault uses XChaCha20-Poly1305 |

  Other ACs and restrictions are N/A for this candidate.
- **Proposed status**: Selected (Bao/hazmat deferred; not v1).

## MVE — Postgres job queue as a hand-written SKIP LOCKED table (sqlx), with apalis-postgres 1.0.0 as the compared library
- **Source**: crates.io API and repos accessed 2026-11-02: `apalis-postgres` 1.0.0 (released 2026-10-12; tags 1.0.0-rc.9 2026-09-16 and rc.10 2026-10-08; depends on `sqlx ^0.9`), repo `apalis-dev/apalis-postgres` files `README.md`, `migrations/*.sql`, `queries/*`; `sqlxmq` 0.6.0 (2025-05-25, depends on `sqlx ^0.8`, last commit 2025-05-25); `pgmq` 0.33.7 (2026-09-14, Rust client depends on `sqlx ^0.8.1`; README: PostgreSQL 14 through 18); PostgreSQL 18 SELECT docs (Locking Clause).
- **Pinned mode**: We will use one `jobs` table in our own migrations, claimed by `UPDATE ... WHERE id IN (SELECT id ... ORDER BY priority DESC, run_at LIMIT n FOR UPDATE SKIP LOCKED) RETURNING *` through sqlx 0.9 on PostgreSQL 18, with inputs (`lane`, `kind`, `payload`, `unique_key`, `run_at`, `priority`) and expect outputs claimed rows with a lease (`locked_by`, `lease_until`), retry counters and a terminal status, on tokio workers. `PgListener` is used only as a wake-up hint; workers also poll.
- **Inputs in the example**: apalis-postgres `get_jobs(worker_id, job_type, count)` is `SELECT id ... WHERE (status = 'Pending' OR (status = 'Failed' AND attempts < max_attempts)) AND run_at < now() AND job_type = v_job_type ORDER BY priority DESC, run_at ASC LIMIT v_job_count FOR UPDATE SKIP LOCKED`, then `UPDATE ... SET status = 'Queued', lock_by = worker_id, lock_at = now()`.
- **Outputs in the example**: claimed jobs per `job_type` (a lane), priority order, `attempts < max_attempts` retries, heartbeat-based orphan re-enqueue (`reenqueue_orphaned.sql`: jobs whose worker's `last_seen` is older than a threshold go back to `Pending`, `attempts = attempts + 1`), a unique index `idx_jobs_idempotency_key ON apalis.jobs(job_type, idempotency_key)`.
- **Project inputs**: thumbnail jobs (reserved lane, AC-10), transcode jobs (AC-11, GPU and CPU capability), scrub, account-deletion cleanup (AC-27); workers on separate machines sharing one Postgres.
- **Project outputs required**: lanes with reserved capacity; retries with GPU-to-CPU fallback (AC-28); at most one job per (kind, blob); recovery of jobs whose worker died; no Redis.
- **Match assessment**: exact match for the hand-written table (every feature maps to one column or one index); apalis-postgres is also an exact feature match but adds weight.
- **If partial or mismatch**:
  - apalis-postgres 1.0.0 is three weeks old at the time of access, went rc.9 -> rc.10 -> 1.0.0 in four weeks, and has 24 migrations in its own `apalis` schema; one migration is `CREATE EXTENSION IF NOT EXISTS hstore;` (contrib extension, extra install-doc burden for AC-22). It also adds `ulid`, codecs and the tower worker stack. Its README does not say how workers fetch jobs, but the SQL above shows SKIP LOCKED. Its sqlx requirement (`^0.9`) matches ours; the cost is the extra moving parts, which conflicts with the owner's simplicity rule.
  - sqlxmq 0.6.0: README lists retries with backoff, in-order channels, keep-alive for long jobs, NOTIFY-based polling; it does NOT mention priorities or unique job keys, and its crates.io dependency is `sqlx ^0.8`, so it would pull a second sqlx major beside 0.9. Last commit 2025-05-25, so it is stale. Rejected.
  - pgmq: README: visibility timeout `vt`; "exactly once delivery" within the timeout; `read_ct` counts reads; the README does not mention priorities, uniqueness, retry limits or SKIP LOCKED. The Rust client depends on `sqlx ^0.8.1` (mismatch with 0.9); the SQL-only install is possible, but it brings its own `pgmq` schema. Rejected for the same reasons.
  - Hand-written pattern authority: PG 18 docs: "Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table." Leases are our `lease_until` column (a claim sets it; a worker extends it by heartbeat; a sweeper query returns expired rows to `queued`); the claim transaction stays short (claim, commit, work outside any transaction), which satisfies the 'short transactions' rule.
  - Lanes and reserved capacity are policy in the worker: one worker pool per `lane` value, thumbnails get at least 1 vCPU (the `00_ac_assessment.md` figure); no library provides this for us either.
- **Restriction/AC binding**:

| Restriction or AC id | Pass / Fail / Verify / N/A | evidence |
|---|---|---|
| Restr: Postgres job queue, no Redis | Pass | SKIP LOCKED in PG 18 docs; apalis-postgres source shows the same pattern |
| AC-10 reserved thumbnail lane | Pass (design) | lane column plus a dedicated worker pool |
| AC-11 adding workers raises throughput | Pass (design) | multiple consumers on a queue-like table is the documented use of SKIP LOCKED |
| AC-28 fallback to CPU on GPU failure | Pass (design) | retry with `attempts` and a `force_cpu` flag in the payload; our code |
| AC-27 account deletion | Pass (design) | `ON DELETE CASCADE` or a delete job |
| Restr: sqlx version match | Pass | hand-written uses sqlx 0.9; sqlxmq and pgmq need 0.8 |
| AC-22 install in 30 min | Pass | no extra extension; apalis would add `hstore` |

## MVE — libvips 8.18 via the `vipsthumbnail` CLI in a sandboxed subprocess (not the Rust crate)
- **Source**: libvips docs and source on github.com/libvips/libvips master (`doc/using-vipsthumbnail.md`, `tools/vipsthumbnail.c`, `man/vipsthumbnail.1`, `libvips/resample/thumbnail.c`, `libvips/foreign/heifload.c`, `libvips/iofuncs/init.c`, `libvips/iofuncs/operation.c`, `libvips/foreign/webpsave.c`); latest release v8.18.7 (2026-09-26, GitHub API); docs page "Library Version: 8.18"; libheif `heif_security.h`; crates.io `libvips` 2.3.0 (2026-06-19, olxgroup-oss), `rs-vips` 0.7.0, `libvips-rs` 8.18.0. Accessed 2026-11-02.
- **Pinned mode**: We will use the `vipsthumbnail` binary of libvips 8.18.x, started with an argument vector (no shell) inside the sandbox of the last candidate, with inputs one source file path (JPEG, HEIC/HEIF, PNG, WebP) and output option strings `--size 320` / `--size 1440` and `--path %s.webp[Q=..,keep=none]`, and expect outputs one 320 px WebP thumbnail and one 1440 px WebP preview with EXIF orientation applied and metadata stripped, on Linux (and macOS for dev).
- **Inputs in the example**: `vipsthumbnail shark.jpg --size 200x100`; `--path` "default `%d/tn_%s.jpg` ... You can add format options too, for example `%c/%s/tn_%s.jpg[Q=20]`"; "`keep=none` almost halves the size of the thumbnail"; recommended set `--size 128 --output-profile srgb --path tn_%s.jpg[optimize_coding,keep=none]`.
- **Outputs in the example**: JPEG/PNG thumbnails; stated process model: "`vipsthumbnail` will process images one after the other. You can get a good speedup by running several `vipsthumbnail`s in parallel".
- **Project inputs**: JPEG and HEIC 12 MP photos (hostile input possible).
- **Project outputs required**: 320 px and 1440 px WebP within 5 s at p95 (AC-10); sandboxed (AC-25).
- **Match assessment**: partial. JPEG shrink-on-load and WebP output match; HEIC has no decoder-level shrink-on-load; `VIPS_BLOCK_UNTRUSTED` blocks HEIC entirely.
- **If partial or mismatch**:
  - JPEG shrink-on-load: `thumbnail.c` `vips_thumbnail_find_jpegshrink`: "Shrink-on-load is a simple block shrink ... Leave at least a factor of two for the final resize step", returning 8, 4, 2 or 1. Doc: "in linear mode none of the very fast shrink-on-load tricks that `vipsthumbnail` normally uses are possible", so never pass `--linear` (slow path).
  - HEIC: no integer shrink. For HEIF, `thumbnail.c` comment: the loader factor "is a gboolean which enables thumbnail load instead of image load. Use the thumbnail if, by using it, we could get a factor > 1.0, ie. we would not need to expand the thumbnail." So the 320 px thumb may come from the file's embedded thumbnail; the 1440 px preview needs a full HEVC decode (my inference; no official timing figure found; `00_ac_assessment.md` estimate 0.3-0.6 s is unverified).
  - `VIPS_BLOCK_UNTRUSTED`: `init.c`: "Set the environment variable `VIPS_BLOCK_UNTRUSTED` to block all untrusted operations on init"; `operation.c`: UNTRUSTED "means the operation depends on external libraries which have not been hardened against attack". `heifload.c` line 1166 sets `operation_class->flags |= VIPS_OPERATION_UNTRUSTED`; `jpegload.c`, `webpload.c`, `pngload.c`, `tiffload.c` have no such flag (grepped). Therefore: setting the variable makes HEIC thumbnails impossible, and leaving it unset allows HEIC, ImageMagick-backed loaders and others. Pin: two worker profiles. Profile A (JPEG/PNG/WebP): `VIPS_BLOCK_UNTRUSTED=1`. Profile B (HEIC only, chosen by magic bytes sniffed in the Rust parent): variable unset, same sandbox. `vips -l` lists the untrusted set; confirm it at image build time (VERIFY: I did not run the binary).
  - libheif limits: `heifload.c` sets, unless `unlimited`: max image 16384x16384 (`0x4000`), `max_total_memory = 2 GiB`, `max_memory_block_size = 1 GiB`, `max_items = 256`. `heif_security.h`: "If you set a limit to 0, the limit is disabled" and `heif_get_disabled_security_limits()` is "Use with care". Never pass `unlimited`. These are default compiled-in limits of libvips, tied to the libheif build (guarded by `HAVE_HEIF_MAX_TOTAL_MEMORY`; VERIFY on the Docker image's libheif). The sandbox memory cap is the real bound.
  - EXIF orientation: `thumbnail.c` reads `vips_image_get_orientation(image)` and swaps target width/height; `tools/vipsthumbnail.c` has `--no-rotate` ("don't auto-rotate"), and `--rotate` is a hidden no-op that prints a warning, so the CLI auto-rotates by default (the man page entry `-t, --rotate` is stale). `heifload.c`: the `autorotate` option "is deprecated and does nothing", rotation is done by the thumbnail operation. `keep=none` strips the metadata after rotation.
  - WebP: `webpsave.c` exposes `effort`, `smart_subsample`, `min_size`; `Q` and `keep` are the standard saver options shown in the docs for `.jpg[...]`; the exact string `[Q=80,keep=none]` for `.webp` is by analogy (VERIFY with one test run).
  - Why the CLI and not the crate: the `libvips` crate README says its calls "have no logic or special behavior in comparison to libvips itself" and warns "the VipsImage object is not thread safe in the moment", and it runs the decoder inside our process, so a decoder bug (libwebp CVE-2023-4863 class, named in `00_ac_assessment.md`) would hit the API/worker process and could not be wrapped in a network-less, memory-capped sandbox without a subprocess anyway. libvips docs: "libvips is threaded and thread-safe, with a few exceptions"; default threads = "as many threads as you have CPU cores" (cap with `VIPS_CONCURRENCY` or sandbox CPU limits). Process start cost per image is expected to be small next to decode; not measured (VERIFY against AC-10).
  - HEVC patents: not resolved by any official page I read (open item in `00_ac_assessment.md`); libvips docs say nothing about licensing of libde265/x265 builds.
- **Restriction/AC binding**:

| Restriction or AC id | Pass / Fail / Verify / N/A | evidence |
|---|---|---|
| Restr: libvips thumbnails in sandboxed workers | Pass | CLI subprocess is sandboxable; crate is not |

## MVE — sandbox for untrusted media workers: Docker Compose container flags on the media-worker service (bubblewrap, nsjail, Landlock compared)
- **Source**: Docker docs (seccomp, Compose services reference, Compose GPU support, NVIDIA Container Toolkit specialized configs); `github.com/containers/bubblewrap` README; `github.com/google/nsjail` README; docs.rs `landlock` 0.4.7 (crates.io updated 2026-07-27), `seccompiler` 0.5.0 (2025-03-07), `birdcage` 0.8.1 (2024-04-19); local runs on Ubuntu host (kernel 7.0.0-38, bubblewrap 0.11.1 host, bubblewrap 0.9.0 in `ubuntu:24.04`, Docker 29.1.3). Accessed 2026-11-02/03.
- **Pinned mode**: We will use Docker Compose container flags on a `media-worker` service (`network_mode: none`, `cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `read_only: true`, `tmpfs`, `mem_limit`, `cpus`, `pids_limit`, `init: true`, `devices`/GPU reservation) with inputs per-job directories on volumes and the Postgres Unix socket, and expect outputs a process tree with no network, hard cgroup CPU/memory/process limits, and a per-job wall-clock kill by the Rust parent, on Linux Docker (macOS VideoToolbox workers run natively and need a separate, unresolved sandbox).
- **Inputs in the example**: Compose docs: "`network_mode: none`: Turns off all container networking"; `mem_limit` "configures a limit on the amount of memory a container can allocate"; `cpus`; `pids_limit` "Caps the number of processes the container can create"; `read_only` "read-only root filesystem"; `cap_drop`; `security_opt` ("boolean options like `no-new-privileges` can omit the value"); `init: true`.

## Findings that change the plan
1. HTTP/2 flow control: hyper's server defaults are 1 MiB per stream and 1 MiB per connection with adaptive window off. At 1 Gbps and 20 ms RTT that caps a connection near 420 Mbit/s, below AC-2's 90%. The server must use a hand-built `hyper_util` accept loop (not bare `axum::serve`) and raise both windows or enable `adaptive_window`; the client-facing hop also depends on the reverse proxy's own settings (not researched).
2. Body limits: streaming handlers bypass `DefaultBodyLimit`; add per-route `RequestBodyLimitLayer` (about 2 MiB on the block route, 50 GiB only on the resumable-upload route). Graceful shutdown has no timeout of its own, so a drain deadline is mandatory.
3. sqlx 0.9.0 is current (2026-05-06) but its own CI tests PostgreSQL 13 and 17, not 18; add a PG 18 job. `PgListener` loses notifications during reconnect, so the account cursor table must stay the source of truth.
4. Job queue: sqlxmq (0.6.0) and pgmq's Rust client depend on `sqlx ^0.8`, a different major than 0.9, and sqlxmq has had no commit since 2025-05-25. apalis-postgres 1.0.0 matches sqlx 0.9 but is three weeks old, needs the `hstore` extension, and has 24 migrations. Recommendation: hand-written SKIP LOCKED table.
5. libvips: `VIPS_BLOCK_UNTRUSTED` blocks the HEIC loader (`heifload` is flagged untrusted), so HEIC needs a separate worker profile that relies on the sandbox alone. HEIC has no decoder shrink-on-load, only embedded-thumbnail selection, so the 1440 px preview needs a full decode (AC-10 risk, unmeasured). The CLI is the sandboxable mode; the Rust crate runs decoders in-process.
6. ffmpeg: `-encoders` lists VAAPI and QSV even where they cannot work; a real test-encode probe is required (shown locally). NVENC allows 12 sessions on this GeForce driver (matches NVIDIA's matrix). `RLIMIT_AS` below 4 GiB breaks NVENC, so use cgroup memory limits. `h264_videotoolbox` is absent from the official codec docs (options only in source). ffmpeg wiki pages (VAAPI, QuickSync) were unreachable (bot wall), so Intel/AMD command lines remain unverified. Hardware H.264 efficiency versus x264 has no rigorous public figure found.
7. Sandbox: bubblewrap cannot run inside a default Docker container (tested: needs seccomp, AppArmor and systempaths all unconfined). Container flags with `network_mode: none` are the practical Compose sandbox, but then the worker reaches Postgres only through a Unix socket volume. macOS workers (VideoToolbox) fall outside this model.
8. Licence: an ffmpeg build with libx264 is GPL; shipping it in the Docker image carries GPL obligations for that image. The official page does not address merely spawning the executable.
