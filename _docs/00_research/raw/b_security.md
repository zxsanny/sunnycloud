## Threat model

### Assets
| # | Asset | Why it matters |
|---|-------|----------------|
| A1 | Non-vault file contents and names of up to hundreds of users | Operator and server compromise expose them (encryption at rest is undefined, see F28) |
| A2 | Vault ciphertext + vault key hierarchy (passphrase, VK, recovery key, per-file keys) | Only confidentiality asset that survives a hostile server |
| A3 | Session/refresh tokens, device tokens (long-lived, full sync access) | A stolen device token = silent full-account read/write |
| A4 | Provider client secrets, Apple .p8, server master secrets | Forge Apple client secret, mint sessions |
| A5 | Share-link tokens and fragments | Bearer capability to files |
| A6 | Worker host / blob volume / Postgres | One decoder RCE should not equal total tenant breach |
| A7 | Desktop endpoints (user laptops) | Daemon runs at login with user rights and a server-controlled file tree |
| A8 | Release signing keys (desktop, Tauri updater, Apple/Windows certs, container signing) | Compromise = code execution on every client |

### Actors
| Actor | Capability |
|-------|-----------|
| Anonymous internet attacker | Hits share links, OAuth callbacks, `/device`, unauthenticated H2 surface; phishing |
| Registered (invited) malicious user | Valid account; IDOR probing, upload abuse, hostile media, hostile filenames, share-link abuse, tries to inject into other accounts |
| Phisher (remote, social engineering) | Device-code and OAuth consent phishing against registered users |
| Malicious or compromised operator / server | Reads all non-vault data; for vault: malicious-server model of ETH papers (S12-S14); serves the JS the web client runs; could push updates if the update channel is the server |
| Local unprivileged user / malware on a client machine | Connects to daemon IPC, reads token file, plants symlinks in the sync dir |
| Supply-chain attacker | Crates, npm, pub, GitHub Actions, base images, ffmpeg/libheif builds, Tauri updater |
| Passive network attacker | Only matters if operator allows plain HTTP (F31) |

Operator trust statement (missing in the draft): for non-vault data the operator is fully trusted; "encrypted at rest" does not defend against the operator. For vault data the operator is untrusted for confidentiality and only partly for integrity (F13-F15).

### Trust boundaries
1. Internet <-> reverse proxy <-> API (unauthenticated surface: OAuth callbacks, `/device`, share links, `/api/auth/*`).
2. Session cookie (web) vs bearer (mobile/desktop) on the same API: two credential types, one CSRF model needed.
3. API <-> Postgres (all tenants in one schema, one DB role).
4. API/blob volume <-> media workers (decoders parse hostile bytes). The draft gives workers a Unix socket to Postgres: this boundary is weaker than it looks (F1).
5. Server <-> clients: clients must treat server-supplied names/metadata/updates as untrusted (zip-slip class on desktop, F20-F21).
6. Daemon <-> settings process (local IPC).
7. Browser origin that serves JS+WASM <-> vault keys in that origin's memory.

## Items confirmed OK
- Identity key (provider, provider user id), never email: correct; nOAuth/pre-hijacking classes are avoided *provided* F4 is fixed (S7, S8).
- Opaque server-side sessions hashed with SHA-256 at rest: fine for high-entropy tokens; no need for a password hash.
- Apple OIDC with no scopes and no PKCE: acceptable (F35).
- XChaCha20-Poly1305 STREAM with final-chunk flag and per-file random key: sound against truncation, reorder, chunk replacement (executed test in the fact card); random 192-bit nonce prefix with per-file key has no birthday problem at 100 MiB. Key non-commitment is low impact for per-file keys (F12).
- Argon2id 64 MiB, t=3, p=1: above the OWASP minimum (R35) and the RFC 9106 low-memory profile except p; the weakness is passphrase entropy, not these numbers (F11).
- Single-owner vault with link sharing only: avoids the public-key sharing surface that produced the MEGA and Nextcloud breaks (S13, R33).
- Blob store with opaque uuid names: no server-side path construction from client names; good.
- Not using a native provider SDK on mobile and using the system browser: right (RFC 8252).
- Postgres job queue with no Redis, no object-store service: fewer trust boundaries.
- Rejecting HTTP/3: no security impact.

## Open questions
1. Operator vs user trust: is it an explicit product claim that a hostile operator cannot read non-vault files? (If yes, "encrypted at rest" needs a different design, F28.)
2. Does the project want inline previews of user files (PDF/SVG/video poster) in the web UI? That decides whether the optional separate content origin is needed (F17).
3. Allowlist format: by email, by provider id, or invite token only? (F4, F5)
4. Is a signed manifest for rollback detection (F13) wanted in v1.1, or is "accepted limitation" enough for the vault description to users?
5. libvips HEIC path: confirm with `vips -l` on the 8.18.7 image which loaders are flagged untrusted, and whether `vipsthumbnail` can unblock only the heif loader; otherwise decode HEIC to PNG in a second sandboxed step. [limited source]
6. tower-http / own Range handler: confirm multi-range behaviour of the chosen static-file code. [limited source]
7. Apple REST docs could not be fetched: confirm `code_verifier` is ignored/accepted and `sub` stability on Team change with a live test (S8 gate).
8. Should device-grant approval be allowed for users who signed in with Apple only (no email to alert)? New-device notice then has to be in-app only.
