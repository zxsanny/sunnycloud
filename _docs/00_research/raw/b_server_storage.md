# Mode B adversarial review: server, storage, database, sync protocol (solution_draft01)

Date: 2026-11-03. Target: `01_solution/solution_draft01.md` + `06_component_fit_matrix.md`. Method: read the problem/AC set, the draft and the prior research (R-S = `raw/storage_db.md`, R-P = `raw/sync_protocol.md`, R-M = `02_fact_cards/mve_server_media.md`), then searched for what they missed. "Analysis" = my own arithmetic or reasoning, not a sourced fact. `[limited source]` = single weak source or search summary only; fetches that returned a summary instead of the primary page are marked.

Overall: no Selected decision has to be reversed. The storage layout (ID-named blobs, tree in Postgres), the per-account counter, axum/hyper/sqlx and the blocklist protocol survive. The draft is thin where two systems must agree (blob dir vs DB: restore, GC, durable resume), where the cursor meets a restored DB, and on the small-file path. Findings 1-7 should become explicit spec text or ACs before decomposition.

| 1 | "Old blob unlinked after commit"; GC as "simple unlink queue"; backup = "easy" (DB dump + blob rsync) | Restore consistency. Blobs are write-once, but LWW overwrite and delete unlink the old blob right away. A dump or PITR taken at T1 and a blob copy taken at T2>T1 can reference blobs GC removed between T1 and T2: a restored DB with missing files. Immich ships "missing files" and "untracked files" checks because this drift is common; Seafile community GC is offline (stops the server) [3rd-party wiki] and trashes libraries first. R-S F10 only says "DB first, files second", which covers orphans but not deletes. | High | S18, S19, S20, R-S F10 | (a) Deletes and overwrites enqueue the blob in a `blob_gc` table inside the same txn; a worker unlinks only after a grace period >= the operator's longest backup interval (default 7 d, configurable). (b) Account deletion (AC-27) uses the same queue with grace 0 and is the only immediate path. (c) Backup doc: dump DB first, then rsync blobs, never run GC in between; restore doc: run the reconciliation (finding 3) after restore. (d) Side benefit: an operator-level undo for accidental deletes without building versions. | AC-27, AC-24, AC-7 |
| 2 | Upload durability: "pre-sized staging file, pwrite at offsets, ack per block, finish by rename, no assembly copy" | The draft never says when a block counts as received. If a block is acked before fdatasync and the server crashes, the persisted "received" bookkeeping says done while the data is zeros (fallocate'd extents read as zero). The final commit is O(1) (AC-4), so it does not re-read the file; the damage surfaces at scrub or on a client download. Out-of-order lanes make "received up to offset N" invalid; it must be a bitmap or set. | High | R-M (AC-3 "fsync then ack per block"), R-S F21/F27, S33 | Spec: the upload session row holds a received-bitmap that is advanced only after `fdatasync` of the staging file (batched, e.g. every 8 MiB or 1 s); a block acked to the client but not yet checkpointed is re-requested after a crash (safe, costs <= 8 MiB, inside AC-3). Final commit: fdatasync, rename, fsync(dir), then DB txn. Whole-file integrity = hash of ordered block hashes (already chosen), so no re-read. | AC-3, AC-4, AC-7, AC-8 |
| 3 | Orphan handling: "GC with grace period" mentioned, sweep design absent; staging + rename | Half-commit windows: (i) crash after rename, before DB commit leaves an orphan; (ii) abandoned staging files hold fallocate'd space (50 GiB each) until swept; (iii) unconstrained sweeping is dangerous: Tinybird deleted live data when its "known objects" snapshot was incomplete. | Med | S20, S18, S5 | Simplest safe design: allocate `blob_id` and insert a `blobs(id, account, state='uploading', reserved_bytes, expires_at)` row at upload start; write the file at its final `blobs/..` path (no rename: a fresh UUID is unreferenced until the commit txn flips `state='live'` and points the node at it). Sweeper A (frequent): rows `uploading` past expiry (24 h) -> unlink + delete row. Sweeper B (rare, merged with the AC-24 scrub walk): files with no row, older than 48 h, are logged first and deleted only after a dry-run flag is flipped; abort the sweep if the DB listing fails or is partial. Drops rename/dir-fsync ordering. | AC-3, AC-4, AC-24 |
| 4 | Small files: 2 commits + 1 PUT per file (R-P: commit -> need list -> PUT block -> commit), 3 fsyncs, 1 txn each | `many-small` (10,000 files 1 KiB-1 MiB) and `tree-100k` are in the data set. Analysis at RTT 20 ms, 4 lanes: 3 sequential round trips = 60 ms/file -> ~150 s for 10,000 files, before server fsyncs (30,000 fsyncs = 15-85 s on a consumer SSD at 350-2,000/s; R-S F27). Nextcloud shows the same wall: ~1 file/s up to tens/s on a 25k-file folder (Oct 2025), and its own "File Packing" bundling was announced to fix per-file overhead. Dropbox's API uses a batch finish (up to 1000 sessions per call) and its staff warn that parallel single-file uploads for one user contend on a lock. | High | S21, S22, S23, R-S F27 | Add two things to the protocol: (1) single-request upload for files <= 2 MiB (one block): `PUT /api/files/{id}/content` with `X-Blake3`, hashed server-side, committed in the same request, 1 RTT, 1 fsync; (2) `POST /api/commits:batch` (<= 500 entries: metadata ops and already-uploaded small files) so one txn/one counter bump covers many files. Server: for batched small blobs, write all files, one `syncfs` (or per-file fdatasync run in parallel), then one DB txn. Add an AC or gate: "10,000 x 100 KiB files from a client at 20 ms RTT finish in <= N s" (N to be set after S1). | AC-5, AC-15, AC-1 |
| 5 | Quota/disk-full: "enforced before accepting a commit" | Check-then-commit races: 100 sessions each pass the check, then the sum exceeds quota or the disk. A check at commit time also wastes the whole transfer. Pre-sizing a 50 GiB staging file by fallocate needs a global free-space guard, or one operator can lock the volume with many open sessions. A full Postgres or WAL volume is worse than a full blob volume (cluster stops). | High | R-S F9, R-S "Design notes", analysis | Reserve at session start: `UPDATE accounts SET reserved = reserved + $n WHERE used + reserved + $n <= quota RETURNING ...` (atomic, one row, same row as the counter or a sibling); release or convert in the commit txn and at expiry. Global guard: refuse new sessions below a free-space watermark on the blob volume (ext4 reserves 5% for root by default; `tune2fs -m 1` on a data volume is an operator note). Cap open upload sessions per account. Keep PG data and WAL on a separate volume with an alert (draft already says separate volumes; make it a hard install check). | AC-4, AC-27, AC-22 |
| 6 | Per-account `seq` counter + cursor `GET /changes?cursor=N`; "tombstones need a retention window" left open | (a) DB restore from backup rewinds `accounts.seq`; devices hold cursors from the future, so new changes with seq <= their cursor are skipped forever (silent divergence). (b) A device offline for 6 months: if tombstones are purged and nothing tells the client, it misses deletes (Syncthing reports exactly this for offline devices past the retention; its default is 15 months in v2.0.14, 6 months in rc/early docs: sources conflict). (c) Microsoft Graph delta answers 410 and a restart link when state is gone. | High | S24, S25, R-P F19 | Cursor = `epoch.seq`. `epoch` is a random id stored in the DB; the restore procedure must change it (or the server detects a lower max seq than any seen cursor). Cursor with a wrong epoch, or seq below `accounts.purge_horizon` (highest purged tombstone seq) -> HTTP 410 `resync_required`; the client enumerates the full tree by file_id and diffs against its synced tree. Because ids are server-assigned, an id present locally and absent on the server is a remote delete, so no resurrection. Purge tombstones after 90 d (configurable), via the same batched job. | AC-5, AC-8, AC-21 |

R-S F22 only compared sequential throughput. | Med | S16, S17, R-S F22 | Make XFS the documented default for the blob volume (no ordered-data journal coupling; likewise good for 50 GiB unlinks) [limited source for XFS side, validate in S6]; keep ext4 supported. | 10 | Tx/pool model: sqlx pool default 10, 100 sessions x 4 lanes, held long-poll | Streaming handlers must never hold a pool connection or open txn across the body stream, nor the long-poll across its 30 s wait. One held connection per session exhausts the pool (400 > 10) and the coderule forbids long txns. No pgbouncer is needed if this rule holds; if it does not, pgbouncer in transaction mode would break `LISTEN`. | Med | R-M (sqlx pool defaults), coderule | Spec rule + test: DB access only at (a) session start, (b) checkpoint every ~8 MiB, (c) commit; long-poll waits on an in-process notifier. | 11 | Counter row in the write txn ("hot row") | Survives, with conditions. A same-row update serializes writers (unavoidable per PG hackers); the lock is held until commit flush, so per-account commit rate ~ 1/flush latency: PLP NVMe ~13k/s, consumer SSD ~300-2,000/s, HDD ~100/s (analysis from R-S F27). A 100k-file first sync of one account is then >= 50 s-5 min of DB time. Dropbox serializes per account too. Danger is only a long txn: taking the counter lock early, or holding it while doing file I/O or a recursive-CTE cycle check. | Med | S21, S32, R-S F27 | Rule: do all reads and the quota check first, `UPDATE accounts SET seq = seq+1 ... RETURNING seq` as the last statement before COMMIT. Moves take the same lock but run the ancestor/cycle check in the same txn (cheap, depth <= ~30). Keep the batch endpoint (finding 4) so one bump covers many files. Document "Postgres on SSD". Do not shard the counter (breaks gapless order). | AC-5, AC-8 |
| 12 | Concurrent folder semantics (move, delete, create) | Gaps in the ID-based model that LWW alone does not answer: (a) move A into B while B is moved into A: cycle; (b) create/upload into a folder deleted concurrently: child under a tombstoned parent; (c) edit of a file whose ancestor was deleted: delete-vs-edit rule undefined (Syncthing makes a conflict copy; "no version history" here means the blob may be gone); (d) deleting a folder with 1M files as 1M tombstones = one huge txn and 1M feed rows. | Med | R-S F6, R-P F5, S25 | Decide and write down: reject cyclic moves (409); creates under a deleted parent get 410 and the client re-creates under the nearest live ancestor; edit-vs-delete: the edit wins (re-create from the uploaded blob) since LWW by commit order, delete-after-edit wins; folder delete writes ONE tombstone for the folder, descendants are purged by a background job and clients delete the subtree locally; descendants stay out of the feed. Add to the sync spec; test with concurrent-device scenarios. | AC-8 |
| 13 | Name policy: "detect NFC/case collisions per folder, refuse or rename" (R-P) | Unspecified fold. "Refuse" makes a Linux-only user's `README` + `readme` fail to sync forever. Dropbox is case-insensitive but case-preserving (staff statement, 2010-2013 posts; current behaviour not re-verified) and still produces conflict artefacts with Linux; Syncthing needed v1.9 to handle case conflicts. | Med | S30, R-P F15 | Store `name` as received plus `name_key` = NFC + Unicode full case-fold computed in Rust with a pinned Unicode version (versioned column); `UNIQUE (parent_id, name_key) WHERE NOT deleted`. Policy: case-insensitive and case-preserving, as every supported desktop OS except Linux is; report collisions as a named sync error on the client. Document the Linux limitation. Test with the draft's "tricky names" set. | AC-8, AC-6 |
| 14 | Blocks stored as a `blocks` table ("tree, blocks, cursor, jobs") | A row per block: 25M files x ~3 blocks = ~75M rows plus a 50 GiB file's 25,600 rows; with ~100 B/row + index that is 7-10 GB extra and write amplification on every overwrite (analysis; R-S estimates 10-15 GB total without it). Listing must not join it. | Med | R-S AC-1 row, analysis | Store the blocklist as one `bytea` (32 B x n; 800 KiB at 50 GiB, TOASTed) on the file revision row; per-block "received" state lives only in the short-lived upload-session row. AC-6 listing query reads only node columns. Revisit a blocks table only if block-level sharing across files is added. | AC-1, AC-6 |
| 15 | `blobs/<2hex>/<2hex>/<uuid>` + PG18 | If node/blob ids move to UUIDv7 (PG 18 `uuidv7()`; good for B-tree locality), the leading hex digits are a timestamp: the two prefix levels would hold almost every new blob in the same dir for hours/years, defeating the fanout. | Low | S26, S27 | Fanout from the last 2 bytes (or from the BLAKE3 of the id) for blob paths, or use random UUIDv4 for blob ids and UUIDv7 only for tree ids. | 16 | Wake-up path: in-process channel now, "Postgres LISTEN/NOTIFY if replicas are added" | NOTIFY inside a txn takes a global commit-time lock held through the flush; Recall.ai took three outages (Mar 2025) from it with tens of thousands of writers; DBOS shows batching NOTIFY avoids it; PG core status disputed (Recall says fixed in core, DBOS says the PG 19 patch does not remove the lock). Not a problem at hundreds of users, but it contradicts "write txns stay independent". | Low | S14, S15 | Single API process: in-process notifier only (as drafted). If multi-replica: send NOTIFY from the app after COMMIT (own connection, batched/coalesced per account per 50-100 ms), never from a trigger inside the write txn. | AC-5, AC-21 |
| 17 | Hash-first upload ("client sends blocklist, server returns missing") | For a new 50 GiB file the client must read and hash 50 GiB before sending byte 1: ~100 s at 500 MB/s SSD (analysis), and the file may change during hashing. For the common new-file case no "need" check is useful. | Med | R-P F3, analysis | Stream mode for new files: hash block k, PUT block k, continue; final commit carries the full blocklist and server compares. ## Contrarian views found

- **"NOTIFY is fine as a wake-up" vs "NOTIFY serializes commits"** (S14 vs S15): both agree the problem needs many concurrent writers; DBOS says batching fixes it, Recall.ai says Postgres core fixed it; they disagree on the core fix. At this project's scale it is a low risk; the draft's in-process design avoids it.
- **ext4 is the default everyone benchmarks** (R-S F22, Phoronix) **vs jbd2 ordered-mode coupling** (S16, S17): throughput benchmarks hide fsync tail latency under mixed load. Source dates are 2017-2019, so a current-kernel measurement is needed (finding 7).
- **"Hash-first, then upload" (Dropbox, Syncthing) vs streaming upload**: practised by the incumbents; our no-dedup, no-delta-for-new-file case gets nothing from the up-front pass (finding 17). My reasoning, not a sourced opinion.
- **Case handling**: some vendor blogs claim cloud backends are case-sensitive (RcloneView), Dropbox staff say case-insensitive/preserving; Dropbox is the more authoritative source, but all are old [limited source].
- **Syncthing retention**: 6 months vs 15 months for the same setting across release notes (S25); do not copy a number, set 90 d and make it configurable.
- **Bundling**: Nextcloud announced File Packing as a 2-10x fix (S22) while a 2025 thread still reports ~1 file/s to tens/s (S23): bundling may not have shipped, or the bottleneck is server-side DB/locking. For us the 1 RTT + batch commit design is cheap enough that we need not wait for a benchmark.
- **No versions / no trash (restriction)**: a buggy client or ransomware on one device propagates deletes and encrypted copies to all devices with no recovery; practitioners treat versions as the real safety net. Accepted by the problem statement; the GC grace period (finding 1) gives operators a partial recovery path at no feature cost.

## Items confirmed OK (draft decisions that survived attack)

- **ID-named immutable blobs, tree in Postgres, no path mirror**: Immich (paths in DB, integrity jobs for drift), Dropbox (ids, atomic moves), oCIS posixfs experimental (R-S F6, F8, F10; S18). The failure modes found (findings 1-3, 19) sit at the blob/DB seam and are fixable with spec text, no layout change.
- **Adjacency list for the tree** (id, parent_id, name_key): moves are one row; 10,000-entry listing is an index range scan on `(parent_id, name_key)` returning ~2 MB, a few to tens of ms server-side (analysis, no benchmark found [limited source]). Materialized path rewrites the subtree on a move, closure tables cost on every move (S34). Ancestor checks (cycle, share-root membership) use a recursive CTE with depth <= ~30. Condition: the listing must not join blocklists (finding 14).
- **Per-account counter in the write txn**: gapless, equals commit order; sequences/outbox ordering problems (R-S F36) avoided; Dropbox also serializes commits per account (S21). Passes with the lock-last rule (finding 11). Shared-folder scope question (R-S open question 3) is moot: only link sharing is in scope.
- **No pgbouncer, no partitioning at ~25M rows, no io_uring**: not needed at 500 users / 112 MB/s (analysis: ~56 block writes/s at 2 MiB; short txns) provided the pool rule in finding 10 holds. [limited source: no benchmark; verify in S6/S1].
- **Postgres job queue with SKIP LOCKED**: standard pattern, no contrary evidence found beyond bloat on a hot table (set fillfactor/autovacuum for `jobs`).
- **PG 18 as the DB**: checksums on by default (S26) closes the "DB pages corrupted silently" gap that R-S F20 only noted for blobs.
- **axum/hyper/sqlx stack**: no open advisory at the pinned versions (S2-S11) given the minimums in finding 9. sqlx RUSTSEC-2024-0363 is behind 0.9.
- **HTTP/3 rejection for v1**: stays; only the mobile multi-connection tweak in finding 20.
- **2 MiB blocks, 4 lanes, 8 MiB resume window**: lane utilization arithmetic (tx 16.8 ms per 2 MiB at 1 Gbps, +20 ms RTT + ack) keeps 4 lanes above link rate (analysis). BLAKE3 at ~2.85 GB/s means hashing is not the bottleneck (R-P F31 measurement).
- **Blocklist size**: 800 KiB per 50 GiB file is fine if stored as one bytea and paged on the wire (finding 14).
