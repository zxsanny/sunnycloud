# AZ-3941 AC-5: an edited file cannot restart by itself

kind: decision (owner)
recorded: 2026-11-21

**Decided 2026-11-22: option (a).** The two-step recovery is accepted and AC-5 of the done spec is amended. No handle-based picker. The Low points below (24 h record expiry without a timestamp, 10 vs 16 MiB wording, `DELETE /sessions/current` revocation delay) stay open.

A `File` from an `<input>` is a snapshot in Chromium: after the file is edited on disk every read throws, so the pre-commit size/`lastModified` check can never see a change. The Worker therefore stops the job (`FileChanged`, record kept) and the person selects the file again, which restarts the upload from the start. No mixed revision is ever committed.

AC-5 words it as an automatic abort and restart. Options: (a) accept the two-step recovery and amend AC-5; (b) schedule a handle-based picker (File System Access API, Chromium only) so the Worker can re-stat the file.

Also open (Low): the 24-hour record expiry has no client-side timestamp (a stale record is removed when its file is selected or its row cancelled); the spec says 10 MiB while spec-gaps G-03-1 says 16 MiB (code asserts 10 MiB).
Server note: `DELETE /sessions/current` returned 204 but `GET /accounts/me` answered 200 for a few seconds before 401: look at session revocation delay.
